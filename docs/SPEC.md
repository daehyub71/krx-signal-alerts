## 1. 프로젝트 목표

국내 상장 전 종목의 일·주·월봉 OHLCV를 다섯 가지 중장기 스윙·추세 전략으로 스크리닝하고,
그 결과를 **매일 아침 08:00 KST 카카오톡 "나에게 보내기"와 이메일**로 받는다.
알림에 다 담기지 않는 신호는 웹 화면에서 이력과 근거값까지 확인한다.

**두 채널의 역할이 다르다** (2026-08-17 추가)

| 채널 | 담는 것 | 왜 |
|------|---------|-----|
| 카카오톡 | 상위 10건 **요약** | 아침에 폰으로 즉시 본다. 본문 200자 상한(R3) |
| 이메일 | **전체 신호 + 조건별 근거값** | 길이 제한이 없다. 앉아서 파고들 때 본다 |

두 채널을 함께 쓰면 서로의 고장을 드러낸다 — 카카오는 리프레시 토큰이 2개월마다 끊길 수 있고(R2),
메일은 그 실패 모드가 없다. **한쪽만 오는 날은 다른 쪽이 고장 났다는 신호**다.

**해결하려는 문제**: 2,763종목을 매일 사람이 훑을 수 없다. 조건에 걸린 종목만 아침에 손에 쥐어 준다.

**이 프로젝트가 하지 않는 것** (명시적 비목표)

| 비목표 | 이유 |
|--------|------|
| 매수·매도 추천, 목표가·손절가 제시 | 투자자문에 해당한다. 신호는 **관찰 후보 목록**이지 주문 지시가 아니다 |
| 실시간·장중 알림 | 데이터가 일봉 종가 기준이다. 장중 신호는 원천적으로 불가 |
| 백테스트·수익률 검증 | 3년치 데이터로는 표본이 부족하다. 별도 프로젝트 주제 |
| 주문 실행·증권사 연동 | 범위 밖 |
| 카카오톡을 여러 사람에게 발송 | "나에게 보내기"는 본인 1명 전용 (친구 발송은 앱 검수 필요). **여럿에게 보내려면 이메일 수신자를 늘린다** (D13) |

### 2-2. D16 — LangGraph를 쓰는 이유와 경계

**이 배치에는 LLM이 없다.** LangGraph는 "지능"이 아니라 **배관**을 준다.
아래 세 가지는 SPEC에 이미 요구사항으로 들어 있던 것이고, 손으로 짜면 매번 틀리는 종류다.

| SPEC 요구 | LangGraph가 주는 것 |
|-----------|---------------------|
| F5~F9 전략 5개 실행 | **병렬 fan-out + reducer 합류** — 노드 5개가 각자 신호 목록을 반환하면 `operator.add`로 합쳐진다 |
| F3 신선도 검사 시 발송 중단 | **조건부 엣지** — 게이트가 그래프 위에 보인다. `if`문이 코드 속에 숨지 않는다 |
| F13c 채널 독립 실패 처리 | **노드별 오류 격리** — 발송 두 노드를 병렬로 두고 각자 결과를 상태에 적는다 |
| N5 시끄러운 실패 | 마지막 `finalize` 노드 한 곳에서만 예외를 올린다 — 실패 판정 지점이 하나다 |
| R7 실행 시간 | 전략 5개와 발송 2개가 실제로 동시에 돈다 |

**경계 (이것을 지켜야 프레임워크가 부담이 되지 않는다)**

- **노드는 얇은 래퍼다.** 전략 계산·랭킹·렌더는 `alerts/` 아래 **순수 함수**로 남고,
  노드는 상태에서 값을 꺼내 함수를 부르고 결과를 상태에 담기만 한다.
- **테스트는 순수 함수를 직접 부른다** (N1·N10). 그래프 테스트는 **연결·분기만** 검사한다.
  전략 로직을 그래프를 통해 테스트하지 않는다.
- **체크포인터를 쓰지 않는다.** 하루 한 번 도는 단발 배치라 중단 재개가 의미 없고,
  상태를 저장하면 시크릿이 디스크에 남는다 (N4).
- **LangGraph를 쓴다고 `langchain-openai` 계열을 끌어오지 않는다.** 의존성은 `langgraph`만.

## 3. 데이터 소스 — 읽기 전용으로 재사용

`krx-stock-charts`가 평일 18:00 KST에 적재하는 테이블을 **읽기만** 한다. 이 프로젝트는 시세를 수집하지 않는다.

| 테이블 | 용도 | 이 프로젝트의 권한 |
|--------|------|-------------------|
| `ksc_tickers` (ticker, name, market, sector) | 유니버스·종목명 | SELECT |
| `ksc_bars` (ticker, timeframe `D`/`W`/`M`, d, o, h, l, c, v, a) | 전략 계산 입력 | SELECT |
| `ksc_meta` (key, value jsonb) | 데이터 기준일 확인 (신선도 검사) | SELECT |

**실측 규모** (2026-08-16 기준)

| 항목 | 값 |
|------|-----|
| 종목 | 2,763 (KOSPI 942 · KOSDAQ 1,821) |
| 봉 | 2,412,261행 (일 1,905,612 · 주 409,898 · 월 96,751) |
| 기간 | 일봉 최대 730 · 주봉 최대 157 · 월봉 최대 37 |
| 거래대금 `a` | **100% 채워짐** (음수 0건, 거래량>0인데 대금=0 0건) |

미충족은 대부분 최근 상장분이다. **봉 부족은 오류가 아니라 정상 skip**으로 처리한다 (F9).

## 4. 기능 요구사항

### 4-1. 공통 파이프라인

**F1. 유니버스 선정**
`ksc_tickers` 전 종목에서 아래를 제외한 목록을 만든다. 제외 사유별 건수를 로그로 남긴다.

| 제외 규칙 | 판정 | 근거 |
|-----------|------|------|
| 스팩 | 종목명에 `스팩` 포함 | 합병 전까지 공모가 고정. 추세 전략이 성립하지 않음 (약 71종목) |
| 우선주 | 티커 6번째 자리가 `0`이 아님 **또는** 종목명이 `우`/`우B`/`(전환)` 등으로 끝남 | 거래 뜸함. OHLC 오차가 종가 대비 0.5%까지 발생 (약 165종목) |
| 유동성 미달 | 최근 20거래일 평균 거래대금 < **5억 원** | 저가·소외주의 거래량 급증 오탐 차단. 임계값은 실측 분포로 조정 (F12) |
| 봉 부족 | 해당 전략이 요구하는 최소 봉 수 미달 | 전략별로 판정. 전역 제외가 아님 |

> 티커는 숫자가 아니다 — `0126Z0`처럼 문자가 섞인 6자리가 실재한다. 검증식은 `^[0-9A-Z]{6}$`.

**F2. 봉 적재**
`ksc_bars`에서 유니버스 전 종목의 일·주·월봉을 읽어 메모리에 올린다.
- 일봉은 최근 **250행**, 주봉 **80행**, 월봉 **37행**(전체)만 읽는다 — MA 워밍업 포함 여유분.
- **Supabase REST는 1000행에서 오류 없이 조용히 잘린다.** 반드시 `range()` 페이지네이션을 쓴다.
- 티커 `.in()` 필터는 URL에 실린다. **300개씩 청크**로 나눈다 (2,763개 한 번에 = URL 19KB → 400).

**F3. 데이터 신선도 검사**
최종 적재 기준일이 **직전 거래일과 다르면 발송을 중단**하고 "데이터 지연"을 알린다.
낡은 데이터로 만든 신호를 보내지 않는다. (§6 R5)

> ⚠ **`ksc_meta`를 판정 근거로 쓰지 않는다** (2026-08-17 실측으로 확인).
> `ksc_meta.update`가 `{"updated": "2026-08-14", "tickers": 200}`을 담고 있었다 —
> 유니버스는 2,763인데 200종목 시절의 기록이 남아 "최신"이라고 말하고 있었다.
> 메타는 **마지막 실행이 무엇을 했는지**를 적을 뿐, 데이터가 실제로 최신인지를 보증하지 않는다.
> 따라서 **`ksc_bars`의 실제 `max(d)`**로 판정한다. 표본이 아니라 SQL 집계로 센다 (R6).

**F4. 전략 실행** — F5~F9 다섯 전략을 각각 순수 함수로 실행한다.
입력은 봉 배열, 출력은 `Signal`(종목·전략·발생일·점수·근거값 dict). 부수효과 없음 → TDD 대상.

### 4-2. 전략 정의

> 아래 임계값은 **초기값**이다. 구현 단계에서 실데이터 분포를 재고 조정하되,
> 변경 시 SPEC에 변경 일자·사유·실측 근거를 남긴다 (워크스페이스 CLAUDE.md 진행 원칙 8).

**F5. MTF 트리플 정배열** — 매일 · 난이도 하 · 최소 월20·주60·일60

세 시간축이 동시에 상승 정렬인 종목. 세 조건 전부 AND.

| 축 | 조건 |
|----|------|
| 월봉 | `종가 > MA20(월)` **그리고** `MA20(월) > 전월 MA20(월)` (월선 상승) |
| 주봉 | `종가 > MA20(주) > MA60(주)` |
| 일봉 | `종가 > MA20(일) > MA60(일)` |

- **신규 진입만 알린다**: 직전 거래일에 조건 미충족 → 당일 충족(= 정배열 전환일)인 종목만.
  이미 몇 달째 정배열인 종목을 매일 보내면 알림이 무의미해진다.
- 점수 = `일봉 종가의 MA20 이격도(%)`가 작을수록 높음 (막 전환한, 덜 오른 종목 우선).
- 예상 신호량: 전환일 조건 때문에 하루 수 건~수십 건.

**F6. 주봉 추세 눌림목** — 주 1회(금요일 마감 기준) · 난이도 중 · 최소 주64

상승 추세 중 20주선까지 밀렸다가 되돌린 주.

| 조건 | 정의 |
|------|------|
| 추세 | `MA20(주) > MA60(주)` **그리고** `MA60(주) > 4주 전 MA60(주)` |
| 20선 터치 | `주간 저가 ≤ MA20(주) × 1.02` |
| 되돌림 마감 | `주간 종가 ≥ MA20(주)` |
| 아래꼬리 | `(min(시가, 종가) − 저가) ≥ (고가 − 저가) × 0.3` |
| 거래량 급감 | `주간 거래량 ≤ 직전 4주 평균 거래량 × 0.8` |

- 점수 = 아래꼬리 비율 × 거래량 감소율. 꼬리가 길고 거래량이 마를수록 높음.
- **금요일에만 산출한다.** 주중에는 미완성 주봉이라 판정이 뒤집힌다.

**F7. VCP 거래량 수축** — 매일 · 난이도 상 · 최소 일60

장대양봉 뒤 조정 없이 거래량만 마르는 구간(Volatility Contraction Pattern).

| 단계 | 정의 |
|------|------|
| ① 기준봉 탐색 | 최근 **20거래일** 안에서 `종가 > 시가`, `(종가−시가)/시가 ≥ 8%`, `거래량 ≥ 직전 20일 평균 × 2.0`인 날. 여럿이면 **가장 최근** |
| ② 경과일 | 기준봉 이후 **3~15거래일** 경과 (너무 짧으면 수축 판정 불가, 길면 패턴 소멸) |
| ③ 몸통 50% 유지 | 기준봉 이후 **모든 날의 종가** ≥ `시가 + (종가−시가) × 0.5` (기준봉 몸통 중간값) |
| ④ 거래량 수축 | 최근 3일 평균 거래량 ≤ 기준봉 거래량 × **0.3** |
| ⑤ 변동성 수축 | 최근 3일 평균 `(고가−저가)/종가` ≤ 기준봉의 `(고가−저가)/종가` × **0.5** |

- 점수 = (1 − 거래량비) × (1 − 변동성비). 둘 다 강하게 마를수록 높음.
- ③이 이 전략의 핵심이자 가장 잘 깨지는 조건이다. 종가 기준으로만 판정한다(장중 저가는 무시) — 그렇지 않으면 거의 모든 후보가 탈락한다.

**F8. 밴드 스퀴즈 & 확장** — 매일 · 난이도 중 · 최소 주72 (52주 + 20주 워밍업)

주봉 볼린저밴드가 최대로 좁혀졌다가 상단을 뚫는 주.

| 항목 | 정의 |
|------|------|
| 밴드 | 주봉 종가 기준 `MA20 ± 2σ`(표본표준편차, ddof=0) |
| BandWidth | `(상단 − 하단) / MA20` |
| 스퀴즈 | **직전 주** BandWidth가 최근 **52주** BandWidth 분포의 **하위 10 백분위 이하** |
| 확장 | 이번 주 BandWidth > 직전 주 BandWidth |
| 돌파 | 이번 주 종가 > 이번 주 상단 밴드 |
| 확인 | 이번 주 거래대금 ≥ 직전 4주 평균 × 1.5 |

- 점수 = BandWidth 확장 배율 × 거래대금 증가율.
- 주봉 기반이지만 **매일 산출한다** — 진행 중인 주봉이 매일 갱신되므로 주중에도 돌파가 잡힌다.
  다만 주가 끝나기 전 뒤집힐 수 있으므로 알림 본문에 `(진행중)`을 표기한다.

**F9. 장기 턴어라운드** — 월 1회(월말 거래일) · 난이도 중 · 최소 월19

오래 눌려 있던 종목에 대량 거래가 들어오는 달.

| 항목 | 정의 | D3(3년 유지) 반영 |
|------|------|-------------------|
| 횡보 구간 | 당월 직전 **6개월** | 원안은 6~12개월. **6개월로 고정** — 월봉 37개에서 12개월 평균(F9-거래량)을 함께 쓰면 탐색 창이 19개월밖에 남지 않는다 |
| 횡보 판정 | `(구간 최고가 − 구간 최저가) / 구간 평균 종가 ≤ 30%` | |
| 거래량 급증 | 당월 거래량 ≥ 직전 **12개월** 평균 × **3.0** | |
| 거래대금 확인 | 당월 거래대금 ≥ 직전 12개월 평균 × **3.0** | D5. 저가주 거래량 급증 오탐 차단 |
| 박스 돌파 | 당월 종가 > 횡보 구간 최고가 | |

- 점수 = 거래량 배율 × 박스 돌파율.
- **월말 거래일에만 산출한다.** 월중에는 미완성 월봉이라 거래량이 과소 집계된다.
- ⚠ **D3의 직접적 대가**: 판정 가능 구간이 19개월이다. 신호가 드물게 나오는 것을 정상으로 본다.
  월 0건이 여러 달 이어져도 고장이 아니다. 월봉을 10년으로 늘리면 해소된다 (기획안 §3-A A-3).

### 4-3. 신호 처리·저장·발송

**F10. 중복 억제**
같은 `(종목, 전략)` 조합이 **최근 10일 이내**에 이미 저장돼 있으면 새 신호로 보지 않는다(저장은 하되 `suppressed=true`로 표시하고 발송에서 제외).
- 월 1회 전략(F9)은 **90일**, 주 1회 전략(F6)은 **28일**을 적용한다.
- 판정 근거는 DB이지 메모리가 아니다 — 배치가 재실행돼도 같은 결과가 나와야 한다.

**F11. 랭킹**
전략별 점수는 스케일이 다르므로 **전략 안에서 백분위로 정규화**한 뒤 전체를 합쳐 정렬한다.
동점이면 거래대금이 큰 종목을 앞에 둔다. 상위 **10개**만 발송한다 (D8).
전략별 최소 1건은 보장한다 — 한 전략이 상위를 독식하면 다른 전략 신호를 놓친다.

**F12. 신호 저장** — `ksa_signals` (§5)
발송 여부와 무관하게 **판정된 모든 신호를 저장**한다. 웹 화면과 중복 억제가 이 이력을 쓴다.

**F13. 카카오톡 발송 — 요약 채널**
`POST https://kapi.kakao.com/v2/api/talk/memo/default/send` (텍스트 템플릿)

- 액세스 토큰 만료 시 리프레시 토큰으로 자동 재발급.
- **재발급으로 새 리프레시 토큰을 받으면 GitHub Secret을 자동 갱신**한다.
  안 하면 옛 토큰으로 계속 시도하다 2개월 뒤 조용히 죽는다.
- `KOE322`(`expired_or_invalid_refresh_token`) 발생 시 **조용히 실패하지 않고 워크플로를 실패**시켜 GitHub 알림이 오게 한다.
- 본문 **200자 상한**. 초과 시 **자르고 보낸다** — 400을 받아 알림이 통째로 사라지는 것보다 낫다.
- 신호 0건이어도 "오늘 신호 없음 (기준일 YYYY-MM-DD)"을 보낸다 (D10).

**F13c. 채널 독립 실패 처리** (2026-08-17 추가)
**한 채널이 실패해도 다른 채널은 반드시 시도한다.** 카카오 토큰이 죽었다고 메일까지 안 가면 안 된다.

1. 두 채널을 각각 try로 감싸고, 결과를 `ksa_runs.detail`에 채널별로 기록한다.
2. 전부 성공 → `status='ok'` / 일부 실패 → `'partial_send_failed'` / 전부 실패 → `'send_failed'`.
3. **하나라도 실패하면 워크플로를 실패 처리**한다 (N5). 부분 성공을 성공으로 위장하지 않는다.
4. 메일이 실패하면 **카카오 본문 끝에 `⚠ 메일 발송 실패`를 붙이고**, 카카오가 실패하면 **메일 제목 앞에 `⚠ 카톡 실패`를 붙인다** — 살아 있는 채널이 죽은 채널을 알려 준다.

**F14. 스케줄**
GitHub Actions cron **평일 08:00 KST** (`0 23 * * 0-4` UTC).
- 한국 공휴일에도 실행되지만 F3(신선도 검사)이 낡은 데이터를 걸러 발송을 막는다.
- 수동 실행(`workflow_dispatch`) 지원.
- **채널 선택 플래그**: `--channel kakao|email|both` (기본 both). 로컬 시험 발송에 쓴다.

## 5. 데이터 모델 — 새로 만드는 것

같은 Supabase 프로젝트에 접두어 **`ksa_`**로 추가한다 (D12). `ksc_*` 테이블은 건드리지 않는다.

```sql
create table if not exists ksa_signals (
  d           date not null,           -- 신호 발생 기준일 (봉의 마지막 거래일)
  strategy    text not null,           -- 'mtf' | 'pullback' | 'vcp' | 'squeeze' | 'turnaround'
  ticker      text not null,
  score       double precision not null,
  rank_no     integer,                 -- 당일 전체 랭킹 (발송 상한에 밀리면 null)
  -- 채널별로 따로 기록한다. 카카오는 상위 10건만, 메일은 전 신호를 담으므로 값이 다르다 (D8)
  sent_kakao  boolean not null default false,
  sent_email  boolean not null default false,
  suppressed  boolean not null default false,   -- 중복 억제로 발송 제외됐는가 (F10)
  evidence    jsonb not null,          -- 조건별 근거값 (F16이 그대로 렌더)
  created_at  timestamptz not null default now(),
  primary key (d, strategy, ticker)
);

create table if not exists ksa_runs (
  run_at        timestamptz primary key default now(),
  data_date     date not null,         -- 사용한 데이터 기준일 (F3)
  universe_n    integer not null,
  signal_n      integer not null,
  sent_kakao_n  integer not null,
  sent_email_n  integer not null,
  -- 'ok' | 'stale_data' | 'partial_send_failed' | 'send_failed'  (F13c)
  status        text not null,
  detail        jsonb                  -- 채널별 성공/실패와 오류 코드 (예: KOE322, SMTPAuthenticationError)
);
```

- `ksa_runs`는 **"안 온 게 정상인지 고장인지"를 사후에 가리는 기록**이다. 발송 실패도 채널별로 남긴다.
- RLS: 읽기는 `anon`/`authenticated`에 공개, 쓰기는 `service_role`만 (`ksc_*`와 동일 방식).
- 예상 규모: 일 수십~수백 행 × 250거래일 ≈ 연 수만 행, 수 MB.

**구현하며 확정한 것** (2026-08-17, `supabase/schema.sql` 적용 완료)

| 항목 | 결정 | 이유 |
|------|------|------|
| `rank` → **`rank_no`** | 컬럼명 변경 | `rank`는 윈도 함수와 이름이 겹쳐 쿼리를 읽기 어렵게 만든다 |
| `ksc_tickers` 외래키 | **걸지 않는다** | 상장폐지로 종목이 지워지면 과거 신호 이력까지 함께 사라진다. 이력은 남아야 한다 |
| 인덱스 `(ticker, strategy, d desc)` | 추가 | F10 중복 억제는 종목축 조회인데 PK가 `(d, strategy, ticker)`라 받지 못한다 |
| CHECK 제약 | 전략 이름 5종 · 티커 `^[0-9A-Z]{6}$` · `status` 4종 | 코드가 놓쳐도 DB가 2차 방어선이 된다 |

검증 완료: service_role upsert 멱등 · anon 읽기 통과 · **anon 쓰기 RLS 차단 확인** · CHECK 제약 3종 동작.

| **R10** | **Gmail 앱 비밀번호 전제** | 구글 계정 **2단계 인증이 꺼져 있으면 앱 비밀번호를 발급할 수 없다**. 일반 계정 비밀번호로는 SMTP 인증이 거부된다(2022년부터 차단) | 2FA를 켜고 앱 비밀번호를 발급한다. 켜기 싫으면 대안: **Resend**(무료 3,000통/월, API 키만 필요, 본인 주소 발송은 도메인 인증 불필요) 또는 **Naver/Daum SMTP**. 발송 계층을 인터페이스로 분리해 교체 비용을 낮춘다 |
| **R11** | **메일이 스팸함으로 갈 수 있다** | 매일 오는 알림이 스팸함에 쌓이면 "안 온 것"과 구분이 안 된다 | 평문 대체본 포함(D15) · 제목에 과장 표현 금지 · **첫 주에 스팸함 확인 후 발신자를 연락처/필터에 등록**. 완료 기준 §9에 포함 |
| **R12** | **두 채널이 같은 배치에 묶여 있다** | 스크리닝 자체가 죽으면 두 채널 다 안 온다 | 채널 이중화는 발송 실패만 막는다. 배치 실패는 GitHub Actions 실패 알림으로 잡는다(N5) — 이 알림도 메일로 온다 |

## 7. 비기능 요구사항

| ID | 요구사항 |
|----|----------|
| **N1** | 전략 5개는 **순수 함수**로 구현한다 — 봉 배열 입력, `Signal` 출력, DB·네트워크 접근 없음. TDD 필수 |
| **N2** | 파이썬 검증 3종 통과: `ruff check .` · `mypy` (strict) · `pytest`. 웹은 `npm run lint` · `npm test` · `npm run build` |
| **N3** | 각 전략은 **손으로 만든 봉 시나리오**로 양성·음성 케이스를 모두 테스트한다. 실DB 드라이런으로 신호량을 확인한 뒤 마일스톤을 닫는다 |
| **N4** | 시크릿(`SUPABASE_SERVICE_KEY`, 카카오 토큰, **Gmail 앱 비밀번호**)은 `.env`/GitHub Secrets에만. `.env`·`.tokens.json`은 `.gitignore`. 로그에 토큰·비밀번호를 찍지 않는다 |
| **N5** | 배치는 **실패 시 반드시 시끄럽게 실패**한다. 예외를 삼키고 0건으로 넘어가지 않는다. 단 발송 단계는 **채널별로 격리**한다 (F13c) |
| **N6** | 배치 재실행이 같은 결과를 내야 한다(멱등). `ksa_signals`는 PK 기준 upsert |
| **N7** | 배포 전 보안 점검 필수 (워크스페이스 CLAUDE.md) — 보안 리뷰 · 시크릿 노출 · CI 권한 · **R4** |
| **N8** | 웹은 알림의 보조 화면이다. 화면 구현 전 `DESIGN.md` 시안 합의를 거친다 |
| **N9** | 발송 계층은 **채널 인터페이스**(`send(subject, summary, full) -> Result`)로 추상화한다. 카카오·메일 구현을 갈아끼울 수 있어야 한다 (R10 대안 전환 대비) |
| **N10** | 메시지 **본문 생성은 순수 함수**로 분리한다 — 신호 목록을 받아 문자열/HTML을 돌려준다. 네트워크 없이 형식을 테스트한다 (200자 절단, 0건 문구, 근거값 전개) |
| **N11** | **LangGraph 노드는 얇게 유지한다** (D16 경계). 도메인 로직은 노드 밖 순수 함수에 있고, 노드는 상태 입출력만 담당한다. 노드 함수 하나가 20줄을 넘으면 로직이 새어 들어온 것으로 본다 |
| **N12** | 그래프 구조를 **문서로 자동 생성**한다 — `graph.get_graph().draw_mermaid()` 결과를 `docs/GRAPH.md`에 커밋한다. 그래프가 바뀌면 문서도 바뀐다 |

## 8. 기술 스택

| 층 | 스택 |
|----|------|
| 배치 오케스트레이션 | **LangGraph** (D16) — 상태 그래프로 단계·분기·병렬·오류 격리를 선언한다 |
| 배치 | Python 3.11+ · `supabase-py`(읽기/쓰기) · 표준 라이브러리 HTTP(카카오) · `pandas`는 쓰지 않음(PLAN §2) |
| 저장 | Supabase PostgreSQL (기존 프로젝트, 접두어 `ksa_`) |
| 스케줄 | GitHub Actions cron (평일 08:00 KST) |
| 알림 ① | 카카오 REST — 나에게 보내기 (요약) |
| 알림 ② | **Gmail SMTP — `smtplib` + `email.message` (표준 라이브러리, 전체 + 근거값)** |
| 웹 | Next.js 16 + TypeScript(strict) + Tailwind · Vercel |
| 테스트 | pytest (배치) · Vitest (웹) |

> 의존성 추가는 사용자 확인 후. 표준 라이브러리로 되면 외부 패키지를 쓰지 않는다.

## 9. 완료 기준

1. 평일 08:00 **카카오톡과 이메일이 모두** 연속 5거래일 도착 (신호 0건인 날의 "없음" 메시지 포함)
2. **메일이 스팸함이 아니라 받은편지함에 들어오는 것**을 확인 (R11)
3. 한 채널을 일부러 실패시켰을 때 **다른 채널이 도착하고, 그 안에 실패 경고가 붙는 것**을 확인 (F13c)
4. 전략 5개 전부 최근 60거래일 드라이런에서 신호를 산출하고, 각 신호의 근거값이 손계산과 일치
5. 웹 `/signals`에서 목록·상세·이력 확인 가능, 배포 완료
6. 파이썬·웹 검증 3종 전부 통과
